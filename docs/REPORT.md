# API/Credential 악용 탐지 설계와 평가

## 1. 목표와 범위

Kubernetes API/Credential 악용을 감사 로그로 탐지하고 정상 사용과 구분한 근거를 남긴다. 탐지 대상은 자격 증명 접근, 원격 실행, 정찰, 권한 변경, 위험 워크로드의 다섯 행동군이다. API 요청의 위험 속성과 신뢰된 작업 승인을 결합한다. 실제 토큰 탈취나 침해 성공을 자동으로 확정하는 시스템은 아니다.

## 2. 입력과 처리

입력은 Kubernetes 감사 이벤트, 정상 조회 프로필, 작업 승인, Role 권한 스냅샷이다. 감사 이벤트의 신원·대상·동작·응답 상태·요청 본문을 정규화하고 같은 요청의 중복 단계를 제거한다. 승인과 일치하는 요청을 확인한 뒤 위험 규칙과 시간 창 집계를 적용한다.

출력은 경보(`findings.json`), 승인 억제 근거(`suppressed.json`), 관측 한계(`observations.json`), 처리 상태(`status.json`)다. 원문 명령·환경 값은 경보에 복사하지 않고 필요한 지문으로 비교한다. 사례의 정상·공격 라벨은 판정 후 채점에만 사용한다.

## 3. 탐지 기준

| 행동군 | 위험 신호 | 정상 판단에 필요한 정보 |
|---|---|---|
| 자격 증명 | Secret get/list/watch, TokenRequest, 토큰용 Secret·API 클라이언트 인증서 발급 | 승인한 민감 리소스·발급 요청과 토큰 일치 |
| 원격 실행 | pods/exec 또는 pods/attach | 대상·명령 지문·작업자·토큰·시간·횟수 일치 |
| 정찰 | API 경로 실패 반복, 다종 목록 조회, 급증·누적 조회량 | 정상 조회 프로필 또는 제한된 승인 |
| 권한 변경 | Secret 읽기·토큰 발급·광범위 권한·권한 위임의 부여 | 실제 Role 권한과 사전 승인 |
| 위험 워크로드 | privileged, hostPID/hostNetwork/hostIPC, hostPath, 위험 capability | 승인한 배포 지문과 보안 속성 일치 |

정찰의 주요 조건은 실패 90초·5건·3경로, 다종 목록 조회 180초·8건·3종류다. 짧은 조회 급증과 계정·리소스별 정상 기준도 적용한다. 규칙은 여러 요청을 함께 볼 수 있지만 임계값보다 느린 정찰에는 한계가 있다.

RoleBinding은 이름만으로 판단하지 않는다. roleRef를 사전 Role 스냅샷과 연결하고 성공한 역할 변경을 상태에 반영한다. 부분 패치로 최종 권한을 알 수 없으면 그 역할의 상태를 무효화한다. 본문 누락·알 수 없는 역할 참조 등은 관측 한계로 남긴다.

위험 워크로드는 컨트롤러의 중첩 Pod 템플릿과 보안 속성을 검사한다. CronJob이나 NodePort를 생성했다는 사실만으로 공격이라 하지 않는다. 위험 속성을 관측해도 실제 컨테이너 실행 여부는 별도 증거가 필요하다.

## 4. 승인과 정상·공격의 경계

작업 승인은 실제 호출자와 작업자, 검증한 개별 credential ID의 SHA-256, 요청 지문, 유효 시간, 최대 요청 수를 묶는다. 토큰이 다르거나 지문·시간·횟수가 맞지 않으면 승인으로 억제하지 않는다. 401/403은 억제하지 않고 5xx는 서버 오류 관측으로 구분한다.

API 권한과 업무 승인은 다르다. 실행 권한이 있는 토큰으로 명령을 성공시켜도 업무 승인이 없으면 경보한다. 반대로 동일한 승인 토큰·동일 요청을 도용자가 사용하면 정상 요청과 관측이 같아질 수 있다.

## 5. 평가 설계

| 자료 | 규모 | 평가 목적 |
|---|---|---|
| 수업 제공 예제 | 정상 1개·공격 3개, 24개 이벤트 | 기본 사례 호환성 |
| API 동작 범위 평가 | 정상 15종·공격 18종, 각각 2회, 158개 이벤트 | 5개 행동군과 정상 대조군의 API 패턴 |
| 실제 실행 통합 평가 | 정상 8종·공격 8종, 각각 2회, 44개 이벤트 | exec·워크로드·권한 효과와 탐지 연결 |
| 외부 공개 로그 | 공격 양성 8개 파일, 14개 이벤트 | 외부 작성 로그에서의 관측 가능성 |

수업 예제는 [수업 공통 저장소 Category 3](https://github.com/cclab-inu/Practical-Cloud-Security-PBL/tree/270bf2df9ae1eddfb26e8dc88cb92326c54a99a8/category3/logs)의 제공 파일이다. 자체 실험의 시나리오·의도 라벨·수집 코드는 **OpenAI Codex의 `gpt-6-astra`**로 작성했다. 감사 로그는 2026-11-17에 해당 코드를 실제 K3s에서 실행해 얻은 실측 자료다. 외부 자료는 **Splunk Attack Data의 Kubernetes Security 관련 True Positive Test**에서 가져온 양성 시험 로그이며 표준 성능 벤치마크가 아니다.

생성 절차는 정상·공격 의도와 요청을 정의하고, 실제 K3s API를 호출한 뒤 응답과 감사 이벤트를 연결해 저장하는 방식이다. 요청 전에 토큰·승인·권한 스냅샷을 고정했다. 실행 통합 자료에는 명령 출력, 컨테이너 상태, 권한 변경 후 실제 접근 증거도 수집했다. 수집된 로그와 증거에 해시를 남기며 실행이나 감사 연결을 확인하지 못하면 무효로 처리한다. 동일 사례의 두 반복을 서로 다른 공격 종류로 세지 않는다. AI 작성 범위, 원본 URL·커밋, 상세 수집 절차는 [출처와 생성 방법](PROVENANCE.md#평가-데이터의-출처와-생성-방법)에 있다.

## 6. 최종 결과

| 평가 | TP | FP | FN | TN | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|---:|---:|
| API 동작 범위: 정상 30·공격 36회 | 32 | 2 | 4 | 28 | 94.1% | 88.9% | 0.914 |
| 실제 실행: 정상 16·공격 16회 | 14 | 4 | 2 | 12 | 77.8% | 87.5% | 0.824 |

수업 기본 4개 사례는 모두 예상 판정과 일치했다. 두 실험은 같은 최종 탐지기를 사용하지만 목적과 사례 구성이 달라 성능의 전후 비교나 하나의 통합 정확도로 해석하지 않는다. API 동작 범위 환경은 worker가 0개여서 정상 exec도 HTTP 400으로 끝났으며 명령 실행 성공을 입증하지 않는다. 실제 실행 환경에는 Ready 노드 1개와 kubelet·containerd가 있다.

TP·FP·FN·TN은 이벤트 수가 아닌 실행 단위다. Precision=TP/(TP+FP), Recall=TP/(TP+FN), F1은 둘의 조화평균이다. 정상 오탐률은 API 동작 범위 평가에서 2/30=6.7%, 실제 실행 평가에서 4/16=25.0%다.

수치: [최종 요약](../results/final-summary.json). 실제 실행의 사례별 근거는 [통합 보고서](INTEGRATION_REPORT.md)에 있다.

### 6.1 최종 구성 요소의 기여

기존 두 자료에서 한 요소씩 제외해 재생했다. 표의 모든 값은 실행 단위 **FP / FN**이다. 새 실환경 실행 없이 최종 설계의 기여를 분석했으며, 두 자료를 합산하지 않는다.

| 구성 | API 동작 범위 66회 | 실제 실행 32회 |
|---|---:|---:|
| 최종 전체 구성 | 2 / 4 | 4 / 2 |
| 작업 승인 제외 | 14 / 2 | 10 / 0 |
| 시간 누적 경보 제외 | 0 / 10 | 4 / 2 |
| 사전 Role 정보 제외 | 2 / 8 | 4 / 2 |
| 워크로드 보안 속성 경보 제외 | 2 / 14 | 2 / 8 |

승인은 정상 관리 오탐을 줄이지만 동일 승인 도용을 놓칠 수 있다. 시간 누적은 정찰을, 사전 Role 정보는 위험 권한 연결을, 워크로드 속성은 위험 배포를 찾는 데 기여했다. 실제 실행 R02에서는 Role 정보를 제외해도 Secret 접근 경보 때문에 TP가 유지되지만 권한 연결 G4 경보는 사라졌다. 시간 누적 경보는 실제 실행 자료에 발생하지 않아 해당 자료에서의 효과를 평가할 수 없다.

시간 누적·워크로드 비교는 해당 경보군을 최종 판정에서 제외한다. 사전 Role 정보 비교는 초기 스냅샷만 비우며 본문 검사와 이후 상태 갱신은 유지한다. 이미 본 자체 자료의 사후 분석이고, 개별 승인 조건이나 일반화 성능의 독립 검증은 아니다. 정확한 방법·사례별 변화·재현 명령은 [기능별 필요성 보고서](COMPONENT_EVALUATION.md)에 있다.

## 7. 오탐과 미탐

| 평가 | 오류 | 이유 |
|---|---|---|
| API 동작 범위 | 정상 인벤토리 FP 2회 | 정상 작업이지만 사전 승인·프로필 범위를 벗어남 |
| API 동작 범위 | 승인 토큰 사용 FN 2회 | 정상과 같은 유효 자격 증명·요청을 사용 |
| API 동작 범위 | 단발 저빈도 정찰 FN 2회 | 집계 임계값보다 적은 요청 |
| 실제 실행 | 정상 privileged 관리 FP 2회 | 사전 승인 등록 누락 |
| 실제 실행 | 정상 권한 거부 점검 FP 2회 | 변경 전 Secret GET 403을 보수적으로 경보 |
| 실제 실행 | 승인 토큰·동일 명령 도용 가정 FN 2회 | 정상 승인과 신원·요청·시간이 동일 |

실제 실행 평가의 오류는 실행 실패나 로그 수집 누락 때문이 아니다. 모든 실행 증거는 유효했고 정상 의도와 경보, 공격 의도와 무경보가 어긋난 사례를 그대로 점수에 포함했다.

## 8. 외부 공개 로그

Splunk attack_data의 양성 자료 8개 중 Secret 조회, privileged Pod 생성, hostPath DaemonSet 생성의 3개에서 경보했다. 낮은 밀도의 익명 스캔, 일반적인 CronJob 생성, NodePort 생성, 이미지 Pull, 단일 Job 생성 거부에서는 경보하지 않았다.

익명 스캔은 시간 창 안의 요청 밀도가 임계값에 미달했다. 나머지 행위는 관측된 설정·빈도만으로 공격이라고 단정하도록 규칙을 만들지 않았다. 따라서 3/8은 해당 공개 사례 집합의 경보 수이며 실운영 탐지율이 아니다. 정상 대조군이 없어 Precision·F1·오탐률은 산출할 수 없다. 이미 참고한 공개 사례를 재생한 검증으로 독립 맹검 평가도 아니다.

## 9. 한계와 적용 조건

자체 설계 소규모 사례와 단일 노드 결과다. 실서비스 사용자 분포·장기 정상 업무·여러 클러스터에 대한 일반적인 성능을 주장하지 않는다. 원문 요청 본문이나 신뢰된 승인·Role 정보가 없으면 일부 판단이 제한된다. 승인 지문은 선택한 보안 관련 필드를 비교하며 모든 의미를 완전히 포괄하지 않는다.

같은 토큰으로 같은 요청을 보내는 도용과 낮은 빈도의 정찰은 관측상 구분이 어렵다. 실제 토큰 탈취, 외부 유출, 컨테이너 탈출, 악성 코드 실행, 실시간 차단·대응 지연은 검증 범위가 아니다. 적용 전에는 장기 정상 데이터, 승인 관리 절차, 추가 세션·실행 관측이 필요하다.
