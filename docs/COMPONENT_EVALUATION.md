# 최종 시스템의 기능별 필요성

AuditGuard의 기능은 서로 다른 판단 문제를 해결한다. 작업 승인은 정상 관리와 악용을 구분할 근거를 제공하고, 시간 누적은 단일 요청에서 드러나지 않는 정찰을 찾는다. Role 정보는 연결된 권한을 해석하며, 워크로드 보안 속성은 실제로 배포하려는 설정의 위험성을 보여준다.

## 기능과 설계 이유

| 기능 | 이 정보가 필요한 이유 | 확인할 수 있는 사례 |
|---|---|---|
| 제한된 작업 승인 | 정상 운영자도 exec·Secret 조회·특권 배포를 수행한다. 위험 API라는 이유만으로 모두 경보하면 정상 업무를 오탐한다. | 정상 exec X01, 승인된 privileged Pod W02, 승인된 hostPath DaemonSet W06 |
| 개별 토큰·요청 지문·시간·횟수 조건 | 한 계정의 승인이 다른 토큰이나 다른 명령까지 적용되지 않도록 허용 범위를 제한한다. | 미승인 토큰 X02, 승인 명령과 다른 X03, 동일 승인 요청을 도용했다고 가정한 X05 |
| 시간 누적 경보 | 정상처럼 보이는 조회도 여러 경로나 리소스로 반복되면 정찰의 근거가 된다. | 익명 경로 탐색 A05, 간격을 둔 조회 A06, namespace를 넘는 조회 A07 |
| 사전 Role 권한 정보 | RoleBinding에는 권한 목록 대신 roleRef가 있다. 역할 이름만으로 Secret 읽기·광범위 권한 여부를 알 수 없다. | 이름이 다른 고권한 역할 연결 A09, cluster-admin 연결 A11, 실제 권한 변경 R02 |
| 워크로드 보안 속성 검사 | Pod·컨트롤러 생성 자체는 정상 동작이다. privileged·hostPID·hostPath 등 내부 설정이 위험 판단의 근거다. | 미승인 privileged W03, hostPID W04, hostPath W05 |

토큰·요청 지문·시간·횟수 조건을 각각 제거한 독립 실험은 아래 비교에 포함하지 않았다. 이 조건들의 역할은 구현과 사례별 정상·공격 판정으로 설명한다. 승인 기능 전체의 효과와 각 조건의 개별 효과를 혼동하지 않는다.

## 비교 방법

기존에 수집·공개한 API 동작 범위 66회와 실제 실행 32회의 로그를 사용해 최종 전체 구성과 한 요소씩 제외한 구성을 비교했다. 새 실환경 실행은 0회다. 두 자료는 목적과 사례 구성이 달라 합산하지 않는다. 정상·공격 정답은 탐지가 끝난 후 채점에만 사용했다.

탐지기 코드·임계값·원본 로그·기존 결과를 그대로 사용했다. 재생 전에 코드 동결과 로그·승인 자료의 해시를 검사하고, 실제 실행 자료의 실행 증거를 검증한다. 전체 구성의 실행별 판정·경보 수·억제 수·규칙 목록이 기존 결과와 일치하는지도 검사한다. 비교용 설정은 메모리에서 복사해 변경한다.

| 비교 구성 | 정확히 제외한 것 | 유지하는 것 |
|---|---|---|
| 최종 전체 구성 | 없음 | 모든 기능 |
| 작업 승인 제외 | work_orders·intents·approvals | 위험 규칙, 정상 조회 프로필, Role 정보 |
| 시간 누적 경보 제외 | 최종 판정에 쓰는 R3·R4·R6·G3·G3-list 경보 | 단일 요청의 민감 접근·exec·권한·워크로드 검사와 승인 |
| 사전 Role 정보 제외 | role_inventory의 사전 스냅샷 | 요청 본문의 Role 검사, 이후 성공한 역할 변경의 상태 갱신 |
| 워크로드 보안 속성 경보 제외 | 최종 판정에 쓰는 G5 경보 | 승인과 다른 행동군 경보 |

경보를 제외하는 두 구성은 해당 경보가 실행 단위 판정에 기여하는 정도를 확인하는 실험이다. 해당 경보는 다른 경보의 입력으로 쓰이지 않으며, 행동군 연쇄 정보는 설명용 관측이다. 내부 계산의 비용이나 처리 속도를 측정한 실험은 아니다. 사전 Role 정보 제외도 RBAC 분석 전체를 제거한 것이 아니다.

## API 동작 범위 66회

정상 30회·공격 36회. 33종을 각각 두 번 실행한 로그의 재생 결과다.

| 구성 | TP | FP | FN | TN | Precision | Recall |
|---|---:|---:|---:|---:|---:|---:|
| 최종 전체 구성 | 32 | 2 | 4 | 28 | 94.1% | 88.9% |
| 작업 승인 제외 | 34 | 14 | 2 | 16 | 70.8% | 94.4% |
| 시간 누적 경보 제외 | 26 | 0 | 10 | 30 | 100.0% | 72.2% |
| 사전 Role 정보 제외 | 28 | 2 | 8 | 28 | 93.3% | 77.8% |
| 워크로드 보안 속성 경보 제외 | 22 | 2 | 14 | 28 | 91.7% | 61.1% |

- **작업 승인:** 제외하면 정상 Secret 조회·토큰 발급·exec·인벤토리·고권한 역할 연결·특권 배포의 12회가 추가 오탐이 된다. 동시에 승인 토큰 도용 가정 H01의 2회는 경보한다. 승인은 오탐을 줄이지만 관측상 동일한 도용을 숨길 수 있다.
- **시간 누적:** 제외하면 A05·A06·A07의 6회를 추가로 놓친다. 반대로 승인 정보 없는 정상 인벤토리 N08의 오탐 2회가 사라진다. 정상 반복 조회와 정찰을 구분하려면 시간 정보와 정상 업무 정보가 함께 필요하다.
- **사전 Role 정보:** 제외하면 A09·A11의 역할 연결 4회를 놓친다. 이름이 바뀐 역할과 잘 알려진 역할 모두 실제 권한 정보로 해석한다. 정상 연결 등도 포함해 알 수 없는 역할 참조가 8건 기록된다.
- **워크로드 속성:** 제외하면 CronJob·StatefulSet·Deployment·Pod·DaemonSet의 위험 설정 A12~A16, 총 10회를 추가로 놓친다. 리소스 종류를 넘어 중첩 Pod 템플릿의 설정을 보는 이유다.

이 자료는 worker가 없는 환경의 API 패턴 평가다. 위 수치는 컨테이너 실행 성공을 증명하지 않는다.

## 실제 실행 32회

정상 16회·공격 16회. 실행 증거가 있는 16종을 각각 두 번 수행한 로그의 재생 결과다.

| 구성 | TP | FP | FN | TN | Precision | Recall |
|---|---:|---:|---:|---:|---:|---:|
| 최종 전체 구성 | 14 | 4 | 2 | 12 | 77.8% | 87.5% |
| 작업 승인 제외 | 16 | 10 | 0 | 6 | 61.5% | 100.0% |
| 시간 누적 경보 제외 | 14 | 4 | 2 | 12 | 77.8% | 87.5% |
| 사전 Role 정보 제외 | 14 | 4 | 2 | 12 | 77.8% | 87.5% |
| 워크로드 보안 속성 경보 제외 | 8 | 2 | 8 | 14 | 80.0% | 50.0% |

작업 승인을 제외하면 X01·W02·W06의 정상 실행 6회를 추가로 경보한다. X05의 동일 승인 토큰·동일 명령 도용 가정 2회도 경보하므로 미탐은 0이 된다. 이때 정상 오탐률은 4/16=25.0%에서 10/16=62.5%로 높아진다. 재현율 하나만으로 승인 없는 구성이 더 좋다고 결론 내릴 수 없다.

워크로드 경보를 제외하면 실제 실행된 W03·W04·W05의 공격 6회를 놓친다. 정상 관리지만 승인이 누락된 W08의 오탐 2회도 사라진다. 보안 속성을 검사하는 기능과 정상 업무를 인정할 승인 정보가 함께 필요한 이유다.

### 전체 점수가 같아도 사라지는 근거

사전 Role 정보를 제외해도 실제 실행 전체 점수는 같다. 그러나 R02의 두 반복에서 **권한 연결 자체의 G4 경보가 사라진다.**

| R02의 요청 순서 | 전체 구성 | 사전 Role 정보 제외 |
|---|---|---|
| 권한 연결 전 Secret GET 403 | 민감 접근 경보 R1 | 민감 접근 경보 R1 |
| Secret 읽기 RoleBinding 생성 201 | 권한 변경 경보 G4 | 역할 참조를 해석하지 못했다는 관측만 기록 |
| 같은 토큰의 Secret GET 200 | 민감 접근 경보 R1 | 민감 접근 경보 R1 |
| 실행 단위 판정 | TP | TP |

Secret 요청이 이미 경보하므로 실행 단위 TP는 유지된다. 하지만 어떤 권한 변경이 접근을 가능하게 했는지에 대한 탐지 근거는 약해진다. API 동작 범위 자료의 A09·A11처럼 권한 연결만 관측한 경우에는 실제 미탐으로 이어진다.

시간 누적 경보를 제외해도 이 자료의 점수는 같다. 실제 실행 자료는 exec·워크로드·권한 효과를 검증하려고 구성했으며, 누적 정찰 경보가 발생한 실행은 없다. 이 자료만으로 시간 누적 기능의 효과를 판단할 수 없다.

## 해석의 범위

이 비교는 **최종 시스템의 어떤 기능이 현재 사례의 판정과 근거에 기여하는가**를 설명한다. 이미 결과를 알고 있는 자체 자료의 사후 분석이며 독립적인 일반화 검증은 아니다. 기능 전체나 경보군을 제외한 효과가 개별 조건 모두의 필요성을 증명하지 않는다. 제거 구성끼리 새 임계값을 조정하거나 결합 효과를 탐색하지 않았다.

한 기능이 항상 오탐과 미탐을 동시에 줄이는 것은 아니다. 승인에는 동일 승인 도용의 한계가 있고, 시간 누적과 위험 설정 검사에는 정상 업무 오탐이 남는다. 외부 공개 로그의 결과와 실제 실행 최종 성능은 기존 값 그대로다.
