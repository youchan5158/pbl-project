# 실제 실행 환경 통합 검증 계획

기존 B5 탐지 소스·설정·66회 데이터와 결과를 보존한다. `data/behavior-eval/freeze.json`의 모든 해시가 유지되는지 검사하고, 통합 검증은 새 모듈과 별도 데이터 디렉터리에서 수행한다. 기존 66회는 API 요청 단계 평가로, 새 실험은 실행 결과를 포함한 통합 평가로 구분한다.

## 검증할 질문

1. 실행 중인 Pod에서 승인된 exec가 실제로 성공하면서 B5 경보가 없는가?
2. API 권한은 허용되지만 업무 승인이 없는 exec 또는 승인 범위를 벗어난 exec가 실제 성공하고도 탐지되는가? RBAC가 거부하는 요청도 별도 대조군으로 보존한다.
3. 일반 워크로드와 승인된 관리 워크로드는 오탐하지 않고, 미승인 위험 설정을 가진 워크로드를 실행한 경우 경보하는가?
4. 역할 연결 전에는 거부되던 접근이 연결 후 실제 허용되는가? 낮은 권한과 높은 권한, 승인된 변경과 미승인 변경을 구분하는가?

## 환경과 증거

프로젝트 전용 QEMU Linux VM에 K3s 서버·kubelet·컨테이너 런타임·네트워크·스케줄러를 구성한다. localhost 포트만 노출하고 Windows 호스트의 폴더를 VM에 공유하지 않는다. 위험 설정의 확인은 VM 안의 전용 더미 파일과 무해한 명령으로 제한한다.

exec는 HTTP 코드만으로 성공이라 하지 않는다. 스트리밍 연결, 명령 출력, 종료 코드, 실행 Pod의 UID/노드/컨테이너 ID를 기록한다. 워크로드는 Pod Running/Ready 및 컨테이너 실행 또는 종료 상태, 필요 시 무해한 관측 출력을 기록한다. 권한은 같은 토큰의 변경 전후 요청 결과와 실제 더미 리소스 접근 여부를 기록한다. 토큰·Secret 원문·개인 키는 제출 자료에 넣지 않는다.

## 공정한 비교

수집기와 전송 프로토콜은 개발용 smoke 실험으로 점검한다. 정식 사례와 기대 실행 조건을 미리 기록하고 수집 전에 해시를 고정한다. 업무 승인과 권한 스냅샷은 측정 요청 전에 생성한다. 라벨은 탐지 후 채점에만 사용한다.

동일한 새 원본 로그에 기존 B4와 동결된 B5를 적용한다. 수집·실행 검증 실패는 정상/탐지 성공으로 채점하지 않고 무효 기록으로 남긴다. 기존 결과와 새 결과는 표본 구성이 다르므로 각각 보고하고 대응 가능한 사례의 실행 단계와 판정 변화를 따로 비교한다.

새 실험에서도 자체 설계·한 클러스터·소수 사례라는 한계는 유지된다. 전체 침해 공격이나 컨테이너 탈출 성공을 주장하지 않는다. 이번 검증의 목적은 실제 컨테이너 실행과 권한 효과라는 빠져 있던 증거를 보완하는 것이다.
