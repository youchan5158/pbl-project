# 실제 컨테이너 실행 통합 평가

## 1. 실험 목적과 구성

탐지기가 정상 작업과 공격 의도의 요청을 구분하는지 검사하고, 컨테이너 실행과 권한 효과까지 별도 증거로 확인했다. 정상 8종·공격 8종을 각각 두 번 수행한 **32회**, 측정 API 감사 이벤트는 **44개**다. 수집·실행 증거가 무효인 실행은 0회다.

실험은 2026-11-17에 Windows 안의 전용 QEMU VM에서 수행했다. 2 vCPU, RAM 4 GiB, 별도 가상 디스크를 사용했다. K3s v1.35.2+k3s1의 Ready 노드 1개에서 kubelet과 containerd 2.1.5-k3s1이 동작했다. VM에 Windows 폴더를 공유하지 않았다. [환경 기록](../data/integration-eval/environment.json), [이미지 digest](../lab/integration-image.json).

입력과 판정은 수집한 실제 로그의 배치 분석이다. 실시간 차단이나 실제 침해 성공을 검사한 것은 아니다. 모든 명령은 실험용 무해한 동작이고 Secret과 hostPath 파일은 더미 자료다.

시나리오·의도 라벨·수집 코드는 **OpenAI Codex의 `gpt-6-astra`**로 작성했다. [사례 정의](../lab/integration_scenarios.py)를 바탕으로 요청·승인 계획을 사전 저장하고, [수집 코드](../lab/integration_live.py)로 실제 K3s 요청을 실행했다. API 서버의 감사 이벤트를 요청과 연결하고 exec 출력·컨테이너 상태·권한 전후 응답을 별도 증거로 저장했다. 따라서 AI는 시나리오와 코드를 작성했고, 평가 로그와 실행 결과는 실환경에서 관측했다. 전체 자료의 출처는 [PROVENANCE.md](PROVENANCE.md)에 있다.

## 2. 실행 증거

| 검증 대상 | 확인 결과 |
|---|---|
| 측정 exec | 성공 8회, RBAC 거부 2회 |
| 워크로드 | Running/Ready 16개 |
| 권한 변경 후 접근 | 동일 토큰의 403 → 201 → 200 전이 6회 |

### 정상·미승인 exec

성공한 8회는 HTTP 101 연결뿐 아니라 stdout `EXEC_CONFIRMED\n0\n`, 명시적 종료 코드 0, 스트림 종료를 확인했다. Pod UID, 노드, containerd 컨테이너 ID도 기록했다. UID 0은 컨테이너 사용자이며 호스트 침해를 뜻하지 않는다.

승인된 정상 명령은 경보를 억제했다. API 권한은 있지만 업무 승인이 없거나 명령이 승인과 다른 요청은 실제 실행되더라도 경보했다. RBAC가 거부한 403은 성공한 실행과 구분해 시도로 경보했다.

성공한 exec 응답에 Audit-ID가 없는 경우 요청별 무작위 User-Agent와 정확한 URI의 유일한 완료 이벤트를 찾고, 사용자·credential ID·대상·응답을 대조했다. 임의 식별자는 요청 연결용이며 정상·공격 정답을 담지 않는다. [정상 실행 증거](../data/integration-eval/proofs/X01-01.json), [미승인 실행 증거](../data/integration-eval/proofs/X02-01.json).

### 위험 워크로드

| 설정 | 실제 관측 | 의미 |
|---|---|---|
| privileged | `CapEff=000001ffffffffff`, SYS_ADMIN 비트 | 넓은 컨테이너 권한 적용 |
| hostPID | 컨테이너에서 `PID1=init` | VM 호스트 PID 공간 관측 |
| hostPath | 실험용 확인 문자열 읽기 | VM 안의 더미 파일 마운트 확인 |

16개에는 일반 Pod/Deployment 4개, privileged Pod 6개, hostPID Pod 2개, hostPath DaemonSet 4개가 있다. 관리자가 수행한 내부 확인 명령은 실행 증명에만 사용했고, 탐지 평가에는 측정 대상 작업자의 워크로드 생성 요청을 넣었다. [privileged 증거](../data/integration-eval/proofs/W03-01.json), [hostPID 증거](../data/integration-eval/proofs/W04-01.json), [hostPath 증거](../data/integration-eval/proofs/W05-01.json).

### 권한 변경 후 실제 접근

대상 ServiceAccount의 같은 토큰으로 변경 전 GET 403을 확인하고, 다른 작업자가 RoleBinding을 생성해 201을 받은 뒤, 토큰 재발급 없이 다시 GET을 보냈다. 변경 후 200뿐 아니라 응답 객체의 종류·이름·더미 내용도 확인했다. 6회 모두 같은 토큰의 접근 권한 변화가 관측됐다.

Pod 조회 권한 연결과 Secret 조회 권한 연결을 구분했다. 탐지기는 roleRef를 사전 Role 스냅샷으로 해석한다. 권한을 연결한 실습 계정은 이미 권한 부여 권한을 가졌으며 RBAC 취약점을 우회한 실험은 아니다. [권한 효과 증거](../data/integration-eval/proofs/R02-01.json), [감사 로그](../data/integration-eval/logs/R02-01.jsonl).

## 4. 최종 성능

| TP | FP | FN | TN | Precision | Recall | F1 | 정상 오탐률 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 14 | 4 | 2 | 12 | 77.8% | 87.5% | 0.824 | 25.0% |

공격 16회 중 14회를 찾고 2회를 놓쳤다. 정상 16회 중 4회에 경보했다. 전체 32회는 독립 공격 32종이 아니며, 하나의 실행에서 나온 여러 경보를 여러 정답으로 계산하지 않는다.

## 5. 오탐·미탐 이유

**W08 오탐 2회:** 정상 관리 목적이지만 사전 승인이 등록되지 않았다. privileged 설정은 실제로 존재하므로 위험 신호를 관측했지만 정상 의도를 알 수 없었다. 승인 관리 누락이 경보 부담으로 이어지는 사례다.

**R03 오탐 2회:** 승인된 권한 연결과 변경 후 조회는 억제했으나, 변경 전 정상 점검의 Secret GET 403은 경보했다. 401/403을 승인으로 억제하지 않는 보수적인 정책 때문이다. 거부 요청을 모두 공격이라고 확정할 수는 없다.

**X05 미탐 2회:** 도용자가 유효한 승인 토큰으로 같은 시간·대상·명령·횟수의 요청을 한다고 가정했다. 감사 로그와 승인 정보가 정상 작업과 같아 구별하지 못했다. 토큰을 훔치는 과정 자체를 수행한 실험은 아니다.

이 여섯 실행을 점수에서 제외하거나 정답을 바꾸지 않았다. 실행 증거는 유효하며 오류는 탐지 판정과 작업 의도의 불일치다.

## 6. 재현성과 한계

사전 요청 계획, 요청 전 승인·토큰 식별·Role 스냅샷, 실제 환경, 감사 이벤트와 실행 증거를 보존한다. 탐지·수집 코드와 증거의 해시를 검사하고 같은 입력에서 같은 판정이 나오는지 재생 검증한다. 사용자 설명 문서는 측정 당시 원본 기록과 별도로 관리한다. [실행 증거 검사 결과](../results/integration/final/execution-verification.json).

단일 노드·한 Kubernetes 버전·자체 설계 16종에 한정된다. exec·워크로드·권한 효과와 수반된 Secret 접근에 초점을 맞춘 실험이므로 모든 행동군의 실운영 성능으로 일반화하지 않는다. API 동작 범위 평가와 외부 공개 로그는 목적과 사례 구성이 다른 별도 검증이다.

토큰 탈취·유출·컨테이너 탈출·실제 악성 코드, 장기 정상 업무, 다중 사용자 경쟁, 실시간 차단·대응 지연은 검증하지 않았다. 정상과 같은 토큰 사용을 구분하려면 추가 세션·실행 관측이 필요하다. [재현 방법](INTEGRATION_LAB.md), [전체 평가](REPORT.md).
