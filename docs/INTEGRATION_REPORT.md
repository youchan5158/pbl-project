# 실제 컨테이너 실행을 포함한 통합 검증

2026-11-17에 실제 kubelet·containerd가 동작하는 노드에서 **16개 사례 × 2회 = 32회**를 실행했다. 44개의 측정 API 감사 이벤트와 실제 실행 증거를 수집했으며, 수집·실행 무효는 0회다. 기존 B4/B5 탐지 소스와 기준을 변경하지 않았다.

이번에 보완한 부분은 **성공한 컨테이너 명령, 위험 설정의 실행 효과, 권한 변경 이후 실제 접근**이다. 기존 66회 API 단계 결과와 별도로 보관한다. 실제 환경에서 수집한 로그를 배치 탐지기에 넣어 판정한 통합 실험이며, 실시간 차단 시스템의 검증은 아니다.

## 1. 이전 환경과 무엇이 다른가

| 항목 | 기존 66회 평가 | 새 32회 통합 평가 |
|---|---|---|
| K3s | v1.35.2+k3s1, agentless | 동일 버전, 서버와 실행 노드 활성화 |
| kubelet / containerd | 없음 | kubelet v1.35.2+k3s1 / containerd 2.1.5-k3s1 |
| 실행 노드 | 0 | Ready 노드 1개 |
| 승인된 정상 exec | HTTP 400, 실행 확인 불가 | HTTP 101 + 출력 + 종료 코드 0 |
| 승인 명령과 다른 exec | HTTP 400, 실행 확인 불가 | HTTP 101 + 출력 + 종료 코드 0 |
| 위험 워크로드 | API 객체 생성·수정 | 실제 Running/Ready 및 설정 효과 확인 |
| RBAC | 변경 요청·감사 로그 | 같은 토큰의 403 → 연결 201 → 실제 조회 200 |

Windows 안의 프로젝트 전용 QEMU VM에 2 vCPU, 4 GiB RAM, 별도 가상 디스크를 사용했다. VM에는 Windows 폴더를 공유하지 않았다. hostPath로 읽는 파일은 VM 안의 전용 더미 파일이다. 이미지 manifest/config/layer digest를 [이미지 잠금 파일](../lab/integration-image.json)에 기록했다. 자세한 실제 버전과 Node Ready 조건은 [environment.json](../data/integration-eval/environment.json)에 있다.

## 2. 실행 성공을 확인한 근거

### 정상·미승인 exec

실행 중인 동일한 진단 Pod에 임시 ServiceAccount 토큰으로 접속했다. 명령은 무해한 `printf`와 `id -u`다. 성공한 8회 모두 stdout이 `EXEC_CONFIRMED\n0\n`, 종료 코드가 0이고, WebSocket v5 채널을 정상 종료했다. Pod UID·노드명·`containerd://...` 컨테이너 ID도 저장했다. `0` 출력은 컨테이너 사용자 UID이며 호스트 침해를 뜻하지 않는다.

여기서 **업무 미승인과 RBAC 거부를 구별**한다. X02/X03은 API 권한이 있어서 명령 자체는 성공한다. 다만 X02는 작업 승인이 없고, X03은 승인된 명령과 실제 명령의 지문이 다르므로 경보한다. X04는 RBAC 자체가 거부해 HTTP 403이며 실행 성공으로 세지 않는다.

성공한 exec는 프록시 때문에 응답에 Audit-ID가 없을 수 있다. 이는 [Kubernetes 감사 API 소스의 설명](https://github.com/kubernetes/apiserver/blob/master/pkg/apis/audit/types.go)과 일치한다. 요청마다 무작위 User-Agent 식별자를 만들고, 정확한 URI에 대응하는 완료 이벤트가 하나뿐인지 확인한 후 서버의 auditID를 가져왔다. 이어서 사용자와 토큰 credential ID 해시를 검증했다. 라벨이나 사례 이름은 요청 식별자에 넣지 않는다. 종료 코드는 [Kubernetes v4/v5 스트리밍 상태](https://github.com/kubernetes/client-go/blob/master/tools/remotecommand/v4.go)를 해석하며 HTTP 101만으로 실행 성공을 판정하지 않는다.

예: [X01 실행 증거](../data/integration-eval/proofs/X01-01.json), [X02 실행 증거](../data/integration-eval/proofs/X02-01.json), [X03 감사 로그](../data/integration-eval/logs/X03-01.jsonl).

### 위험 워크로드

16개 워크로드 모두 Pod가 실제 Running/Ready가 되고 컨테이너 내부에서 검증 명령이 성공했다. 구성은 일반 Pod/Deployment 4개, privileged Pod 6개, hostPID Pod 2개, hostPath DaemonSet 4개다. 정상 승인 및 한계 대조군도 포함한 수다.

| 설정 | 실행 효과의 증거 | 이 증거가 의미하는 범위 |
|---|---|---|
| privileged | 실제 Pod 설정 + `CapEff=000001ffffffffff`, SYS_ADMIN 비트 확인 | 넓어진 컨테이너 권한이 실제 적용됨 |
| hostPID | `hostPID: true` + 컨테이너에서 `PID1=init` 관측 | VM 호스트의 PID 공간을 볼 수 있음 |
| hostPath | 실제 마운트 + `AUDITGUARD_VM_ONLY_FIXTURE` 읽기 성공 | VM의 지정된 파일을 컨테이너에서 읽음 |

관리자 검증 exec는 **실행 증명용**이고, 탐지 평가에는 해당 작업자가 보낸 워크로드 생성 요청만 넣었다. 따라서 G5가 관리자 검증 명령을 보고 맞춘 것이 아니다. G5는 생성 요청의 보안 속성을 판단하고, 별도 실행 증거가 그 설정이 실제 적용됐음을 확인한다. 컨테이너 탈출이나 운영 자격 증명 탈취는 수행하지 않았다.

예: [privileged 증거](../data/integration-eval/proofs/W03-01.json), [hostPID 증거](../data/integration-eval/proofs/W04-01.json), [hostPath 증거](../data/integration-eval/proofs/W05-01.json).

### 권한 변경 후 실제 접근

각 사례의 대상 ServiceAccount는 처음에는 해당 권한이 없다. 같은 토큰으로 GET을 보내 `403`을 확인하고, 별도 작업자가 RoleBinding을 생성한 뒤 **토큰을 재발급하지 않고** 같은 GET을 보냈다. 마지막에는 `200`뿐 아니라 응답 객체의 종류·이름과 실제 내용을 확인했다. Secret은 실습용 더미 값과 일치하는지만 확인하고 값 자체는 증거 파일에 저장하지 않았다. 6회 모두 `403 → 201 → 200` 전이를 확인했다.

R01은 Pod 조회 권한, R02/R03은 Secret 조회 권한이다. RoleBinding 요청에는 권한 내용이 직접 없으므로, B5는 측정 전에 저장한 Role 스냅샷에서 연결 대상 역할의 권한을 찾는다. R02에서는 G4가 민감한 권한 연결을, R1이 Secret 접근을 각각 탐지했다. 변경 작업자는 실습용 namespace의 권한 부여 권한을 이미 가진다. RBAC 취약점을 우회해 권한을 얻은 실험은 아니다.

예: [R02 실행 증거](../data/integration-eval/proofs/R02-01.json), [동일 토큰의 전후 감사 로그](../data/integration-eval/logs/R02-01.jsonl).

## 4. 수치와 비교 방법

| 평가 | TP | FP | FN | TN | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 기존 API 평가 B5: 정상 30·공격 36회 | 32 | 2 | 4 | 28 | 94.1% | 88.9% | 0.914 |
| 새 통합 평가 B4: 정상 16·공격 16회 | 10 | 4 | 6 | 12 | 71.4% | 62.5% | 0.667 |
| 새 통합 평가 B5: 동일 32회 | 14 | 4 | 2 | 12 | 77.8% | 87.5% | 0.824 |

새 B5의 정상 오탐률은 4/16 = 25.0%다. 이번 수치가 이전보다 낮다는 사실도 숨기지 않는다. **코드가 바뀐 전후 성능 비교가 아니라, 같은 코드에 다른 사례 구성을 적용한 결과**다. 특히 승인 누락 정상 관리 작업과 정상 권한 거부 점검을 넣어 운영상의 경보 부담을 드러냈다. 두 데이터셋을 합쳐 하나의 정확도나 실서비스 오탐률로 발표하면 안 된다.

동일한 새 32회에서 B5는 B4가 놓친 위험 워크로드 6회를 추가 탐지했다. B4가 오탐한 승인된 정상 exec 2회는 B5가 정상으로 판단했다. 반면 승인 등록이 빠진 정상 privileged 작업 2회를 B5가 추가로 경보했고, 승인 토큰 그대로의 도용 2회는 B5가 승인으로 받아들여 놓쳤다. 그래서 **전체 FP는 B4와 B5 모두 4회**이며, B5가 오탐까지 줄였다고 말할 수는 없다.

이전 정상 exec N03의 400은 새 X01에서 실행 성공 101·종료 코드 0으로 보완됐고 B5 판정은 정상으로 유지됐다. 이전 승인 불일치 A04의 400은 새 X03에서 실제 실행 성공으로 보완됐고 경보도 유지됐다. 이전 RBAC 거부 A03과 새 X04는 둘 다 403·경보다. 이전 원본 로그와 판정을 수정한 것은 아니다.

외부 Splunk 자료는 알려진 공격 양성 8개 중 3개 경보로 그대로다. 이번에 외부 벤치마크가 추가된 것은 아니고, 기존 탐지기를 실제 실행 환경에서 확인한 것이다.

## 5. 오탐·미탐을 어떻게 설명할까

**W08 오탐 2회:** 작업 의도는 정상 관리이지만 탐지기에 사전 승인 정보가 없다. 실제 privileged 실행은 확인되므로 위험 신호 자체가 틀린 것은 아니다. 다만 정상 업무와 공격을 구분하는 과제의 라벨 기준에서는 오탐이다. 정상 승인 누락률에 따라 운영 경보량이 달라진다.

**R03 오탐 2회:** 권한 변경과 변경 후 조회는 정확한 사전 승인으로 억제됐다. 그러나 변경 전 정상 점검의 Secret GET 403은 B5가 승인으로 억제하지 않는다. 현재 규칙은 인증·인가 거부를 보수적으로 경보하므로 전체 정상 작업이 오탐된다. 이 사례를 평가에서 빼거나, 사후에 403을 정상으로 바꾸지 않았다. 향후에는 요청 지문과 예상 거부 결과를 묶은 제한된 점검 승인을 별도 개발 데이터에서 검토할 수 있지만, 이번 B5에는 반영하지 않았다.

**X05 미탐 2회:** 도용자가 유효한 승인 토큰으로 같은 시간·대상·명령·요청 수를 그대로 사용하면 감사 로그와 승인 정보가 정상 작업과 같다. 이번 실험은 토큰을 훔치는 과정이 아니라 이미 가진 토큰으로 사용한다는 가정이다. 별도 세션·기기·행위 증거가 없는 현재 관측만으로 실제 사용자의 의도를 구별할 수 없다. B4가 이를 경보한 이유도 도용을 구별해서가 아니라 승인된 정상 exec까지 모두 경보하기 때문이다.

## 6. 재현성과 남는 한계

측정 전에 소스·설정·사례·실제 요청 계획·환경 정보의 해시를 고정했다. 각 실행 전에 토큰 발급 영수증·업무 승인·Role 스냅샷을 저장하고 API 서버의 시각도 기록했다. 판정에는 사례 라벨을 전달하지 않고, 판정 후 채점한다. 실행 증거가 없거나 감사 이벤트와 연결되지 않으면 무효 처리한다. [실행 증거 검사 결과](../results/integration/final/execution-verification.json)에서 32회를 모두 확인할 수 있다.

공개 저장소에는 최종 평가에 쓰는 원본·승인·결과만 남기고 중간 개발 기록은 제외했다. 수집 당시 [해시 목록](../data/integration-baseline/preserved-files.json)은 동결 증거로 유지하며, 현재 검증은 공개한 최종 자료에 해당하는 항목을 확인한다. [비교 결과](../results/integration/final/comparison.json)에 검사 범위를 명시한다. 해시는 보존·변경 검사 수단이며 제3자 인증은 아니다.

정리 과정에서 평가 도구 `scripts/evaluate_integration.py`의 보존 목록 검사 범위를 조정했다. 이 보고 도구의 원래 해시는 수집 당시 기록에 그대로 남아 있으며 현재 코드와 같다고 주장하지 않는다. 탐지기·수집기·설정·사례 계획의 원본 해시는 계속 검사하고, 최종 수치와 사례별 경보·실행 검증 결과가 정리 전 결과와 일치하는지 재생 검증한다.

한 VM·한 Kubernetes 버전·자체 설계 16종의 제한된 실험이다. 32회는 독립 공격 32종이 아니다. 새로운 실험은 exec·워크로드·권한 효과와 이에 수반한 Secret 접근에 초점을 맞췄으며, 5개 행동군 전부의 새로운 성능 평가로 일반화하지 않는다. 장기 정상 업무, 다중 사용자 경쟁, 다양한 클러스터 구성, 실제 악성 코드·탈출·유출, 실시간 탐지 지연과 대응은 검증하지 않았다.

발표에서는 “API 요청만 시험했던 한계를 보완해 실제 컨테이너 실행과 권한 효과까지 확인했다. 제한된 통합 평가에서 공격 16회 중 14회를 탐지했고 정상 16회 중 4회를 오탐했다. 승인 정보의 누락과 정상 점검은 오탐을, 정상과 관측이 같은 토큰 도용은 미탐을 만들었다”고 설명할 수 있다.
